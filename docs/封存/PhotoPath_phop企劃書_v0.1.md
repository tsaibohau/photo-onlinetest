## 1. 專案摘要

### 1.1 問題
- 展覽、市集、園遊會、校園活動、醫院、地下街和大型商場裡，GPS 訊號常常被建築物遮擋或反射，定位失準甚至完全失效。
- 現有的室內導航方案（Beacon、UWB、Wi-Fi 指紋）都要事先**布建硬體**或**建置場域資料**。臨時活動幾天就結束，根本不划算。
- 現場通常已經有一張「導覽地圖」或「樓層簡介圖」，但它只是一張靜態圖片，不會告訴你「你在哪裡」，也不會告訴你「下一步往哪走」。

### 1.2 解法
`.phop`（**Ph**oto + h**op**）是一種新的檔案格式：**一張自帶導航能力的照片**。
- 檔案內容包含：地圖影像、走道的數學模型（一組二元一次方程式）、錨點（校準點）、地標（POI），以及授權資訊。
- 打開檔案後，使用者先選擇或掃描附近的錨點，系統就知道起點座標。之後靠手機內建的加速度計與方向感測器推算移動，**完全不使用 GPS**。
- 移動只沿著地圖的**上、下、左、右**四個方向，位置永遠吸附在走道線上，藉此抑制累積誤差。

### 1.3 核心差異

| | Beacon / UWB | Google 室內地圖 | **PhotoPath `.phop`** |
|---|---|---|---|
| 需要硬體 | 需要 | 不需要 | **不需要** |
| 建置時間 | 數天到數週 | 由場館申請，耗時數月 | **幾分鐘（拍一張照）** |
| 適合臨時活動 | 不適合 | 不適合 | **適合** |
| 離線可用 | 部分 | 不可 | **可（檔案在手機裡）** |
| 成本 | 高 | 免費，但無法自己控制 | 低 |

## 2. 產品定義與使用流程

所有 `.phop` 檔案都**只能在 PhotoPath 網站上製作**。網站提供兩種製作方式。

### 2.1 方式一：免費版（一般使用者，未授權檔案）
**目標**：一般使用者在活動現場拍下導覽圖，幾秒內就能得到一份可以導航的檔案。原則是**以程式自動判斷為主**。

```
拍照 / 上傳
  → 自動校正透視（把斜拍的地圖拉正）
  → 品質檢查（模糊？反光？地圖不完整？）
  → OCR + 影像分析：找出每個物件（攤位、房間、出入口、廁所…）和它的名稱
  → 自動挑選錨點（校準點）候選
  → 自動推測走道，轉成方程式
  → 使用者確認或微調
  → 下載 .phop（標記為未經授權，只能在這台裝置上開啟）
```

**辨識失敗時的三層退路：**

| 狀況 | 系統行為 |
|---|---|
| 自動辨識成功 | 直接進入確認畫面，使用者只需要按「確定」 |
| 辨識不足（信心值太低、標籤太少、模糊、反光） | 請使用者**重拍**，並給具體提示：「靠近一點」「避開燈光反射」「讓整張地圖入鏡」「手機與地圖保持平行」 |
| 重拍 2 次仍然失敗 | 改成**手動標點**：保留已辨識到的部分，讓使用者自己補畫走道、點選錨點 |

**授權限制**：檔案內寫入 `UNLICENSED`（未經授權）標記，並與下載時的裝置綁定，**其他裝置無法開啟**（做法見 §3.4）。

### 2.2 方式二：授權版（付費主辦方）
**目標**：主辦方製作正式的活動導覽，發給所有參加者使用。

主辦方在**編輯畫面**可以設定：
- **定點導覽**：每個 POI 的名稱、介紹文字、圖片、開放時間
- **指引**：預設路線，例如「參觀動線」「無障礙動線」「逃生路線」
- **闖關打卡**：設定關卡點、抵達條件（掃現場 QR，或走進某段走道範圍）、完成獎勵訊息
- **錨點**：每個錨點可以附一張實體 QR，貼在現場，供參加者掃描定位

完成後可以：
- **下載** `.phop` 檔案
- **產生 QR code**：任何人掃描後，都能在任何裝置的瀏覽器裡直接開啟

### 2.3 Phase 0：全部免費
在正式收費與專案完成之前：
- 網站的建置參數設為 `VITE_BILLING_ENABLED=false`。Phase 0 沒有伺服器，所以是建置時的開關，不是伺服器設定。
- **任何人都可以使用兩種製作方式**，不需要登入。
- 檔案格式**照樣寫入 license 欄位**，這樣日後開始收費時不需要改格式，舊檔案也能繼續相容。

## 3. `.phop` 檔案格式規格

### 3.1 基本資訊

| 項目 | 值 |
|---|---|
| 副檔名 | `.phop` |
| MIME type | `application/x-phop` |
| 容器格式 | ZIP，結構仿照 EPUB 和 DOCX |
| 格式辨識 | ZIP 的**第一個檔案**必須是未壓縮的 `mimetype`，內容是 `application/x-phop`。所以檔案第 30 個位元組開始可以直接讀到 `mimetypeapplication/x-phop`，不必解壓縮就能判斷格式 |
| 規格版本 | `phop/0.1` |

### 3.2 目錄結構

```
example.phop  (ZIP)
├── mimetype                 ← 第一個檔案，不壓縮
├── manifest.json            ← 明文：版本、場地、座標系、檔案清單
├── license.json             ← 明文：授權類型、裝置綁定資訊
├── payload/                 ← 授權版：明文
│   ├── map.webp             ← 校正後的地圖影像
│   ├── graph.json           ← 走道方程式、節點、邊
│   ├── anchors.json         ← 錨點
│   ├── pois.json            ← 物件與地標（免費版由 OCR 產生）
│   ├── calibration.json     ← 每段走道的比例
│   ├── tour.json            ← 授權版：導覽與指引路線
│   └── checkpoints.json     ← 授權版：闖關打卡
├── payload.enc              ← 免費版：把 payload/ 打包後加密，取代上面的 payload/
└── signature.sig            ← Phase 1 才有：Ed25519 簽章
```

### 3.3 主要 JSON 結構

**manifest.json**
```json
{
  "format": "phop/0.1",
  "id": "8f3c2a1e-…",
  "title": "2026 春季手作市集",
  "createdAt": "2026-11-14T10:00:00+08:00",
  "creator": "photopath-web/0.1",
  "mode": "UNLICENSED",
  "coordinateSystem": {
    "origin": "top-left",
    "xAxis": "right",
    "yAxis": "down",
    "unit": "px",
    "width": 2000,
    "height": 1400,
    "allowedDirections": ["up", "down", "left", "right"]
  },
  "floors": [{ "id": "F1", "name": "1F", "z": 0 }],
  "files": {
    "payload/map.webp":  "sha256-…",
    "payload/graph.json": "sha256-…"
  }
}
```

**graph.json**：走道就是一組二元一次方程式。
```json
{
  "lines": [
    { "id": "L1", "a": 0, "b": 1, "c": 100, "range": [0, 400],   "floor": "F1" },
    { "id": "L2", "a": 1, "b": 0, "c": 50,  "range": [100, 300], "floor": "F1" },
    { "id": "L3", "a": 1, "b": 0, "c": 350, "range": [100, 300], "floor": "F1" }
  ],
  "nodes": [
    { "id": "N1", "x": 50,  "y": 100, "lines": ["L1", "L2"] },
    { "id": "N2", "x": 350, "y": 100, "lines": ["L1", "L3"] }
  ],
  "edges": [
    { "from": "N1", "to": "N2", "line": "L1", "lengthPx": 300 }
  ]
}
```
- 每條走道寫成 `a·x + b·y = c`。
- **只允許**水平線（`a=0, b=1`，也就是 `y = c`）或垂直線（`a=1, b=0`，也就是 `x = c`）。
- `range` 是走道在另一個軸上的有效範圍：水平線限制 x，垂直線限制 y。
- `nodes` 是兩條走道的交點，由克拉瑪公式算出（§4.2）。

**anchors.json**
```json
[
  { "id": "A1", "name": "東側入口", "x": 50,  "y": 300, "line": "L2",
    "qr": "phop:A1", "facingUp": true },
  { "id": "A2", "name": "服務台",   "x": 350, "y": 300, "line": "L3",
    "qr": "phop:A2", "facingUp": true }
]
```

**calibration.json**：每段走道各自的比例（§5）。
```json
{
  "defaultPxPerStep": null,
  "segments": [
    { "line": "L2", "pxPerStep": 5.0,  "source": "walk",  "samples": 1 },
    { "line": "L1", "pxPerStep": 3.33, "source": "walk",  "samples": 1 }
  ]
}
```

**license.json**
```json
{
  "type": "UNLICENSED",
  "notice": "本檔案未經主辦方授權，僅供下載者本人於原裝置使用",
  "issuedAt": "2026-11-14T10:00:00+08:00",
  "deviceBinding": {
    "keyId": "d2b7…",
    "alg": "AES-GCM-256",
    "iv": "base64…"
  },
  "billing": { "phase": 0, "enforced": false }
}
```
授權版的 `type` 是 `"ORGANIZER"`，並且沒有 `deviceBinding`。

### 3.4 授權與裝置綁定（Phase 0 沒有後端，全部在瀏覽器完成）

**免費版（UNLICENSED）**
1. 使用者第一次進入網站時，瀏覽器用 WebCrypto 產生一把 **AES-GCM 256 位元金鑰**，設定 `extractable: false`（不可匯出），以 `CryptoKey` 物件存在 IndexedDB，並另外產生一個隨機 `keyId`。
2. 打包時，`payload/` 先壓縮成一包，再用這把金鑰加密成 `payload.enc`。
3. `manifest.json` 和 `license.json` 保持明文，所以任何 Viewer 都能讀出「這是未經授權的檔案」，並顯示提示。
4. 在別的裝置開啟時，IndexedDB 裡找不到相同 `keyId` 的金鑰，解密失敗，Viewer 顯示「此檔案未經授權，僅能在原裝置開啟」。
5. 地圖影像本身也會加上半透明的「未經授權」浮水印。

**授權版（ORGANIZER）**
- Phase 0：`payload/` 不加密，`signature.sig` 不存在，Viewer 不驗證簽章。所以任何裝置都能開。
- Phase 1：由 Cloudflare Worker 用伺服器端的 **Ed25519 私鑰**對 `manifest.json` 簽章（manifest 已包含每個檔案的 SHA-256），Viewer 內建公鑰來驗證。**私鑰絕對不能放在前端。**

**QR code（無後端版本）**
- 主要做法：QR 內容是 `https://photopath.pages.dev/view#src=<檔案網址>`。檔案由主辦方放在任何**允許跨域讀取（CORS）**的公開網址，例如 GitHub Pages、Cloudflare R2 公開 bucket、自己的網站。Google Drive 的分享連結通常不允許跨域讀取，需要在文件中提醒。
- 小檔案做法：如果只有走道和錨點、沒有地圖影像（純向量圖），把 JSON 壓縮成 deflate + base64url 後直接放進 URL 的 `#` 後面。`#` 後的內容不會被送到伺服器，完全離線可用。
- Phase 1：平台代管檔案，QR 改成短網址 `https://photopath…/p/{id}`。

**誠實揭露的限制**
- 這種裝置綁定只擋得住「PhotoPath 的 Viewer」，擋不了使用者直接截圖地圖、或另外寫程式解析檔案。它的定位是**標記與嚇阻**，不是銀行等級的 DRM。
- 使用者清除瀏覽器資料後，裝置金鑰就跟著消失，原本下載的免費檔案也會打不開。重新拍一次即可。

## 4. 定位系統：二元一次方程式座標、不使用 GPS

### 4.1 座標系
- 原點在地圖的**左上角**，x 往右、y 往下，單位是影像像素。這是影像處理的慣例；畫面上要顯示數學座標時，再把 y 翻轉即可。
- 「上」的定義是**地圖影像的上方**，不是地理上的北方。整個系統都不需要知道真正的北方在哪裡。

### 4.2 走道 = 二元一次方程式，路口 = 聯立方程式的解
每條走道 `Lᵢ: aᵢ·x + bᵢ·y = cᵢ`。兩條走道的交點就是二元一次聯立方程式的解，用**克拉瑪公式**計算：

```
D  = a₁·b₂ − a₂·b₁
x  = (c₁·b₂ − c₂·b₁) / D
y  = (a₁·c₂ − a₂·c₁) / D
```
- `D = 0` 表示兩條線平行，沒有交點。
- 算出的交點還必須落在**兩條線各自的 `range` 內**，才是真正的路口。

因為只允許水平和垂直兩種走道，`D` 只會是 0 或 ±1，計算完全精確，沒有浮點誤差的問題。這也是限制「只能上下左右」的另一個好處。

### 4.3 開啟檔案時，怎麼知道使用者的座標？
沒有 GPS，所以**由使用者告訴系統起點**。確定起點之後，地圖才展開。

| 優先順序 | 方式 | 說明 |
|---|---|---|
| 1 | **掃描現場錨點 QR** | 最準。同時記錄朝向基準 θ₀（§6.3） |
| 2 | **從清單選擇附近的錨點** | 清單依名稱排序，例如「東側入口」「服務台」「3 號攤位」。免費版的錨點名稱來自 OCR |
| 3 | **在地圖上點自己的位置** | 系統吸附到最近的走道點，並請使用者「面向地圖上方」以設定 θ₀ |

### 4.4 移動模型：只能上下左右
```
每偵測到 1 步：
  dir  = 量化方向（上 / 下 / 左 / 右）    ← §6
  line = 目前所在的走道
  如果 dir 和 line 的走向平行：
      沿 line 前進 1 步 × 這段走道的 pxPerStep
      碰到走道端點就停住（不能穿牆）
  否則（例如走在水平走道上卻偵測到「往上」）：
      記為「待轉向」
      如果目前位置距離某個路口在容許範圍內（例如 2 步）：
          吸附到路口，換到垂直的那條走道
      否則忽略這一步（大多是感測器雜訊）
```
- 位置**永遠只會落在走道線上**（map matching），所以不會飄到牆裡或攤位裡。
- 沒有斜向移動，就不會產生斜向的角度誤差累積。誤差只剩「沿著走道多走或少走了幾步」，而這種誤差在下一個錨點就會被歸零。

### 4.5 抑制累積誤差
1. **錨點歸零**：使用者每經過一個錨點（掃 QR，或按「我在這裡」），位置直接重設成錨點座標。
2. **端點截斷**：走到走道盡頭就停住，多出來的步數直接丟掉。
3. **路口吸附**：在路口附近偵測到轉向時，把位置校正到路口座標。
4. **漂移提示**：連續走了 N 步都沒經過錨點（預設 150 步），畫面提示「位置可能有誤差，請在下一個錨點確認」。

### 4.6 未來擴充到 3D
座標從 `(x, y)` 擴充成 `(x, y, z)`，走道變成空間直線的向量式 `P = P₀ + t·d`，方向向量 `d` 限定在 ±x、±y、±z 這六個方向。樓層之間以「樓梯節點」或「電梯節點」連接（只沿 z 軸），並可用氣壓計輔助判斷樓層變化。

## 5. 難題一：示意圖沒按比例、面積未知

### 5.1 核心想法
**導航不需要知道真實面積。**它只需要兩樣東西：
- **拓撲**：哪條走道接哪條走道、路口在哪裡。示意圖再怎麼不按比例，拓撲通常是對的。
- **相對比例**：在這段走道上，走一步大約對應地圖上幾個像素。

### 5.2 分段比例
示意圖常常是「左半邊畫得比較寬、右半邊被壓扁」。所以比例**不是全圖一個值**，而是**每一段走道各自一個值** `pxPerStep`，水平和垂直方向也各自獨立。這樣不管示意圖怎麼變形，每一段都能自己修正。

### 5.3 取得比例的三種方式

| 方式 | 誰做 | 精度 | 說明 |
|---|---|---|---|
| **校正走路** | 主辦方 | 高 | 在編輯器按「開始校正」，從錨點 A 實際走到錨點 B，系統自動記錄每段走道的步數，換算成 `pxPerStep` |
| **輸入已知距離** | 主辦方 | 中 | 例如「攤位寬 3 m」「走道長 40 m」，再用平均步長（約 0.7 m，可調整）換算成步數 |
| **群眾學習** | 系統自動 | 隨使用人數提升 | 使用者從錨點 A 走到錨點 B 並確認後，**經過同意**匿名回傳這段的步數，取中位數更新比例。需要 Phase 1 後端 |

### 5.4 沒有比例時（大多數免費檔案）
改用**節點跳躍模式**：
- 指引的單位是「路口」，不是「公尺」，例如「往右直走，在第 2 個路口左轉」。
- 走道上的位置以**進度百分比**顯示，起始比例先用全圖估計值：`走道像素長度 ÷ 估計步數`。
- 使用者每次在錨點或路口確認位置，系統就用「實際走的步數」反推這段走道的 `pxPerStep`，**一邊用一邊校正**。

## 6. 難題二：手機拿反，方向判斷錯誤

**情境**：使用者往地圖上方走，但手機是倒著拿的。如果系統只看「手機頭部指向哪裡」，就會判斷成往下走。

**解法採多層防護：**

### 6.1 第一層：看「人往哪走」，而不是「手機指向哪」
- 每走一步，人的身體在水平面上會有前後方向的加速度擺動。
- 把加速度轉到世界座標系（用重力和磁力計），取一個步伐週期內的水平加速度，做**主成分分析（PCA）**，第一主軸就是行進的**軸線**。
- PCA 只能得到軸線，分不出前後（有 180° 的不確定性）。這部分用步伐的相位關係判斷：腳跟著地瞬間，前進方向的加速度先負後正，和垂直加速度峰值有固定的相位差。
- 這樣算出的方向和手機怎麼拿無關。

### 6.2 第二層：偵測手機姿態
- 從加速度計取重力向量 `g = (gx, gy, gz)`，換算到手機自己的座標軸：
  - `gy > 0`（重力指向手機頭部）→ **手機上下顛倒**
  - `gz > 0`（重力指向螢幕正面）→ **螢幕朝下**
- 手機顛倒時，如果方向是從磁力計的 heading 推出來的，就加 180° 修正。

### 6.3 第三層：用錨點對齊，不信任「北方」
- 在錨點掃 QR 時（錨點 QR 規定貼成「掃描者面向地圖上方」），或在地圖上設起點時（提示「請面向地圖上方」），記錄當下的感測器方位角 **θ₀**。
- 之後的方向一律用**相對角度**計算：`rel = (heading − θ₀ + 360) mod 360`。
- 室內的鋼筋結構會讓磁力計整體偏移，但相對於 θ₀ 的變化通常仍然可信。每到一個新錨點就重新記錄 θ₀，偏差就會被重置。

### 6.4 第四層：用地圖檢查合理性
以下任一情況，系統判斷「方向可能顛倒了」，自動翻轉 180°，並以震動和畫面提示使用者確認：
- 預測位置**連續撞到走道端點**，也就是一直撞牆。
- 使用者確認了下一個錨點，但這個錨點落在「預測方向的反方向」。
- 走過的步數已經超過預測方向上剩餘走道長度的 1.5 倍。

### 6.5 第五層：手動備援
畫面上常駐一顆「**⇅ 方向反了**」按鈕。按一下就讓 θ₀ 加 180°，並把最近 N 步的位移反向重算。

### 6.6 量化成 4 個方向（含遲滯）
```
rel = (heading − θ₀ + 360) mod 360        // 0 = 地圖上方，順時針
k   = round(rel / 90) mod 4               // 0 上, 1 右, 2 下, 3 左
dev = |rel − k·90|（取 0~45 之間的角度差）
if dev > 35°：  沿用上一個方向             // 斜著走時不要亂跳
else：          dir = k
```
最後一行的 35° 是遲滯門檻：只有在方向夠接近四個正方向之一時才更新，避免使用者斜走時方向在兩者之間來回跳動。

## 7. 編碼流程（具體步驟與虛擬碼）

### 7.A 免費版：從照片到 `.phop`（全部在瀏覽器執行）

| 步驟 | 動作 | 使用技術 |
|---|---|---|
| A1 | 拍照或上傳照片，限制長邊不超過 3000 px | `<input type="file" accept="image/*" capture>` |
| A2 | 偵測地圖四角，做透視校正、拉直 | OpenCV.js：Canny → findContours → approxPolyDP → warpPerspective |
| A3 | **影像品質檢查** | 清晰度：Laplacian 變異數 < 100 判定模糊；反光：HSV 亮度 > 250 的像素佔 > 5% 判定反光；四角偵測失敗判定地圖不完整 |
| A4 | **OCR**：取得每個文字框的內容、位置、信心值 | Tesseract.js，語言 `chi_tra+eng`，語言檔自己架在網站上 |
| A5 | **物件偵測**：找出矩形區塊（攤位、房間），把文字框對應到包含它的區塊，形成「物件 + 名稱」 | OpenCV：adaptiveThreshold → findContours → boundingRect |
| A6 | **錨點候選**：依關鍵字和分布挑選 | 關鍵字表：入口、出口、服務台、詢問處、廁所、電梯、樓梯、Entrance、Info…；優先挑在地圖上彼此分散的物件 |
| A7 | **走道推測**：物件以外的空白區域就是走道 | 二值化 → 骨架化（Zhang-Suen）→ HoughLinesP → 只保留接近水平或垂直（±10°）的線段 → 合併共線線段 → 轉成 `a·x+b·y=c` |
| A8 | **求路口**：兩兩用克拉瑪公式求交點，保留落在 range 內的 | §4.2 |
| A9 | **錨點吸附**：每個錨點投影到最近的走道上 | 點到水平線距離是 `|y−c|`，到垂直線是 `|x−c|` |
| A10 | **結果檢查**：判斷要不要重拍 | 見下方門檻表 |
| A11 | 使用者確認或微調（可以拖曳錨點、增刪走道） | Canvas 編輯器，畫線工具只允許水平或垂直 |
| A12 | 地圖加浮水印，轉成 WebP | Canvas `toBlob('image/webp', 0.85)` |
| A13 | 打包 payload，用裝置金鑰加密 | JSZip + WebCrypto `AES-GCM` |
| A14 | 組合最外層 ZIP（`mimetype` 放第一個且不壓縮）並下載 | JSZip `STORE` 模式 → `a[download]` |

**A10 重拍判定門檻**（初始值，需要實測調整）：

| 指標 | 合格條件 |
|---|---|
| OCR 平均信心值 | ≥ 60 |
| 辨識到的有名稱物件 | ≥ 3 |
| 錨點候選 | ≥ 2 |
| 走道 graph | 連通，而且每個錨點都能抵達 |

全部合格就進入確認畫面。任何一項不合格就提示重拍，並明確告訴使用者是哪一項的問題。累計失敗 2 次，改成手動標點模式，並保留已辨識的結果。

**A13～A14 打包虛擬碼**
```js
async function buildUnlicensed(payloadFiles, meta) {
  const inner = new JSZip();
  for (const [path, data] of payloadFiles) inner.file(path, data);
  const innerBytes = await inner.generateAsync({ type: "uint8array" });

  const { key, keyId } = await getOrCreateDeviceKey(); // IndexedDB，non-extractable
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const enc = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, innerBytes);

  const zip = new JSZip();
  zip.file("mimetype", "application/x-phop", { compression: "STORE" }); // 必須第一個
  zip.file("manifest.json", JSON.stringify({ ...meta, mode: "UNLICENSED" }));
  zip.file("license.json", JSON.stringify({
    type: "UNLICENSED",
    deviceBinding: { keyId, alg: "AES-GCM-256", iv: b64(iv) },
    billing: { phase: 0, enforced: false }
  }));
  zip.file("payload.enc", enc);
  return zip.generateAsync({ type: "blob", mimeType: "application/x-phop" });
}
```

### 7.B 授權版：主辦方編輯器

| 步驟 | 動作 |
|---|---|
| B1 | 上傳原始地圖檔，接受 PNG、JPG、PDF 第一頁。原始檔通常很清晰，可以跳過品質檢查 |

| B9 | 下載 `.phop`；或填入檔案的公開網址，產生 `view#src=…` 的 QR |

### 7.C 開啟檔案：Viewer 導航流程
```
C1  讀取檔案（本機選檔，或從 #src= 抓取）
C2  檢查 mimetype == "application/x-phop"，否則拒絕
C3  讀取 license.json
      UNLICENSED → 從 IndexedDB 找出 keyId 對應的金鑰
                    找不到 → 顯示「未經授權，僅能在原裝置開啟」，結束
                    找到 → 解密 payload.enc
      ORGANIZER  → Phase 1 起驗證 signature.sig
C4  比對 manifest 裡每個檔案的 SHA-256（檢查檔案是否損毀）
C5  載入 graph、錨點、比例
C6  選擇起點：掃錨點 QR > 從清單選錨點 > 在地圖上點選（§4.3），記錄 θ₀
C7  請求感測器權限（iOS 必須由使用者手勢觸發 DeviceMotionEvent.requestPermission()，且網站必須是 HTTPS；Cloudflare Pages 預設就是 HTTPS）
C8  地圖展開，進入導航迴圈：
      偵測步伐 → 量化方向 → 沿走道移動、吸附路口 → 合理性檢查 → 錨點歸零
```

### 7.D 核心演算法虛擬碼

**克拉瑪交點**
```js
function intersect(L1, L2) {
  const D = L1.a * L2.b - L2.a * L1.b;
  if (D === 0) return null;                       // 平行
  const x = (L1.c * L2.b - L2.c * L1.b) / D;
  const y = (L1.a * L2.c - L2.a * L1.c) / D;
  return inRange(L1, x, y) && inRange(L2, x, y) ? { x, y } : null;
}
// 水平線 (a=0,b=1) 檢查 x 是否在 range；垂直線 (a=1,b=0) 檢查 y
function inRange(L, x, y) {
  const v = L.a === 0 ? x : y;
  return v >= L.range[0] && v <= L.range[1];
}
```

**步伐偵測**
```js

```

**沿走道移動**
```js
function onStep(state, dir) {
  const L = state.line;
  const horizontal = L.a === 0;
  const parallel = horizontal ? (dir === "left" || dir === "right")
                              : (dir === "up"   || dir === "down");
  if (parallel) {
    const sign = (dir === "right" || dir === "down") ? 1 : -1;
    const d = sign * pxPerStep(L);
    if (horizontal) state.x = clamp(state.x + d, L.range);
    else            state.y = clamp(state.y + d, L.range);
  } else {
    const n = nearestNodeOn(L, state, 2 * pxPerStep(L)); // 容許 2 步誤差
    if (n) {
      state.x = n.x; state.y = n.y;
      state.line = perpendicularLineAt(n, L);
    }
    // 否則視為雜訊，忽略
  }
  sanityCheck(state);   // §6.4
}
```

## 9. 可行性分析

### 9.1 技術可行性

| 模組 | 可行性 | 說明 |
|---|---|---|
| 檔案格式、打包、加密 | 高 | 全部是成熟的標準技術（ZIP、WebCrypto） |
| 透視校正 | 高 | OpenCV 的標準流程；地圖有明顯邊框時效果好 |
| OCR 辨識名稱 | 中 | 印刷體橫書的辨識率不錯；手繪、藝術字、直書、小字、反光時辨識率明顯下降，所以設計了「重拍 → 手動」兩層退路 |
| 走道自動推測 | 中低 | 示意圖風格差異非常大，自動結果大多需要使用者微調。這是免費版最需要實測的部分 |
| 步伐偵測 | 高 | 計步準確率通常在 95% 以上 |
| 步長與比例 | 中 | 步長誤差約 5–10%，必須靠錨點歸零和分段比例來控制 |
| 方向判斷 | 中 | 室內磁力計不可靠；靠「只有 4 個方向」、相對 θ₀ 和地圖合理性檢查補強 |
| 網頁感測器 | 中高 | iOS 需要使用者授權；網頁在背景或螢幕關閉時會停止接收感測器資料，所以導航時要保持螢幕開啟（可用 Wake Lock API） |

**結論**：Phase 0 的所有功能在純前端都做得到。精度目標應該定為**「走道 + 路口等級」**，而不是公分等級。這個精度對臨時活動導覽已經足夠。

### 9.2 市場可行性
- **目標客群**：
  - 展覽與市集主辦單位
  - 校園活動、園遊會
  - 大型研討會
  - 醫院、地下街、商場的臨時動線
  - 實境解謎、闖關活動
- **優勢**：零硬體、幾分鐘就能建置、離線可用；「闖關打卡」對活動主辦方有行銷價值。
- **競品**：Beacon 方案成本高、建置期長；Google 室內地圖需要場館申請、時間長，主辦方也無法自己控制內容。在**臨時、低成本**這個區塊幾乎沒有直接競品。

### 9.3 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| 免費使用者拍的是主辦方的地圖，有**著作權**疑慮 | 中 | 檔案加上 UNLICENSED 標記和浮水印，並綁定裝置；在服務條款中說明「僅供個人使用」；同時引導主辦方改用授權版 |
| OCR 和走道辨識率不足 | 高 | 重拍提示、手動標點；Phase 1 用伺服器端模型輔助 |
| Tesseract 繁中語言檔約 10–20 MB，第一次載入慢 | 中 | 進入 `/create` 頁面時就在背景預先下載，並設定長期快取 |
| 裝置綁定可以被繞過 | 低 | 定位為「標記與嚇阻」，不承諾絕對防護 |
| Phase 0 授權版沒有簽章，可能被偽造 | 低（免費期間沒有金流） | Phase 1 加入 Ed25519 簽章 |
| 室內磁力計偏差 | 中 | §6 的多層防護 |
| `#src=` 網址的檔案主機不允許跨域讀取 | 中 | 文件中列出可用的主機，並建議主辦方直接在本機選檔開啟 |

### 9.4 營運模式（Phase 1 以後）
- 免費版永久免費，作為導流入口。
- 授權版依**活動場次**收費，或依**掃描開啟次數**分級收費。
- 加值服務：闖關數據報表、熱點動線分析（匿名且彙總後的資料）。

## 11. 附錄：計算範例

### 11.1 場地設定
```
y↓   x→   0          50                 350        400
100       ├──────────N1────────L1─────────N2─────────┤
                     │                    │
                     L2                   L3
                     │                    │
300                  A1 東側入口          A2 服務台
```
- L1：`0·x + 1·y = 100`，x 的範圍是 [0, 400]
- L2：`1·x + 0·y = 50`，y 的範圍是 [100, 300]
- L3：`1·x + 0·y = 350`，y 的範圍是 [100, 300]

### 11.2 求路口 N1（L1 和 L2 的交點）
```
D = a₁b₂ − a₂b₁ = 0·0 − 1·1 = −1
x = (c₁b₂ − c₂b₁) / D = (100·0 − 50·1) / −1 = 50
y = (a₁c₂ − a₂c₁) / D = (0·50 − 1·100) / −1 = 100
→ N1 = (50, 100)
```
檢查範圍：x = 50 落在 L1 的 [0, 400] 內，y = 100 落在 L2 的 [100, 300] 內，所以 N1 是有效路口。用同樣方法算出 N2 = (350, 100)。L2 和 L3 都是垂直線，D = 1·0 − 1·0 = 0，平行，沒有交點。

### 11.3 示意圖不按比例：校正走路
主辦方從 A1 走到 A2，路線是 A1 → N1 → N2 → A2：

| 段落 | 走道 | 像素長度 | 實際步數 | pxPerStep |
|---|---|---|---|---|
| A1→N1 | L2 | 200 | 40 | **5.00** |
| N1→N2 | L1 | 300 | 90 | **3.33** |
| N2→A2 | L3 | 200 | 40 | **5.00** |

可以看到水平走道每步只有 3.33 px，垂直走道每步是 5 px。這代表示意圖把橫向**壓縮**了大約 1.5 倍。如果整張圖只用一個比例，就會一路累積誤差；分段比例直接解決了這個問題。

### 11.4 使用者導航
1. 使用者在 A1 掃描 QR → 位置 (50, 300)，所在走道 L2，記錄 θ₀。
2. 往「上」走 40 步 → y = 300 − 40×5 = 100，到達 N1。
3. 偵測到「右」，目前就在 N1，與路口的距離是 0，小於容許的 2 步 → 換到走道 L1。
4. 往「右」走 30 步 → x = 50 + 30×3.33 ≈ 150，位置 (150, 100)，畫面顯示「L1 進度 33%」。
5. 假設手機倒拿，方向被誤判成「左」：
   - 如果沒有修正，x 會往 0 前進，直到撞上 L1 的左端點。
   - §6.1 從步伐判斷的行進方向和磁力計 heading 相差 180°，觸發翻轉，同時提示使用者確認。
   - 位置回到正確的「右」方向繼續累加。
6. 到達 A2，掃描 QR → 位置歸零成 (350, 300)，累積誤差清除。
